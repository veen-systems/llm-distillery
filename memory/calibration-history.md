# Calibration History

Long-arc record of scorer training, calibration, and oracle-prompt experiments — what worked, what didn't, and what shouldn't be retried. Loaded when calibration work starts.

## Dead Ends (don't retry these)

Compact "what we tried, why it failed, don't retry" entries. Pattern adopted from the vmodel pattern cluster — see [ducroq/agent-ready-projects#16](https://github.com/ducroq/agent-ready-projects/issues/16) for the cross-repo tracker. Sibling adoptions: [ovr.news commit 6132725](https://github.com/ducroq/ovr.news/commit/6132725) (shipped 2026-06-05), [ducroq/NexusMind#230](https://github.com/ducroq/NexusMind/issues/230) (pending).

- **Pure embedding + linear/MLP probe as substitute for fine-tuning** (uplifting v5 comparison, 2026-01). 12 embedding+probe combinations tested on uplifting_v5; best (e5-large-v2 + MLP) MAE 0.860 vs fine-tuned Qwen2.5-1.5B 0.680 — **+26.4% worse**. All others 32–48% worse on the dimensional-regression task; multilingual rerun (mpnet / MiniLM / multilingual-e5 / bge-m3) didn't close the gap. Full results in `research/embedding_vs_finetuning/results/uplifting_v5_comparison_report.md`; resolution note in `docs/OPEN_QUESTIONS.md` line 22. **Don't retry** replacing the fine-tuned student with frozen-embedding + probe for nuanced multi-dimensional regression — embeddings capture topic, not quality. Commerce binary classification is the exception (embeddings won 98.3% vs 97.8% F1, kept as `base_prefilter`).

- **Naive PyTorch dynamic INT8 quantization on Gemma-3-1B** (#24, 2026-03-07). Uplifting v6 val 50-article benchmark: 2.6× faster, 3.3× smaller — but MAE jumped FP32 0.749 → INT8 **1.378 (+0.63)**. FP16 on CPU emits NaN (no native x86 FP16 compute). Per-tensor dynamic quant with no calibration data destroys the score head and attention layers. Full benchmark in `docs/experiments/quantization-benchmark-2026-03-07.md`. **Don't retry** `torch.quantization.quantize_dynamic` as a one-line speedup — it nearly doubles MAE. The remaining viable paths on #24 are ONNX Runtime calibrated INT8, GGUF / llama.cpp, or smaller base-model retrain (Qwen2-0.5B uplifting reached MAE 0.760, see `docs/OPEN_QUESTIONS.md`).

- **Orthogonal-lens prompt design** (thriving v1, 2026-03 → PARKED 2026-04). Prompt added explicit "NOT Belonging" exclusion clauses + removed `social_cohesion_impact` to force semantic orthogonality between lenses. Result over 2 training attempts: val MAE 1.09 → 0.97, calibrated test MAE **0.94** vs uplifting v7 at 0.787 on the same Thriving tab. Bimodal score distribution (sparse 2–5 dead zone, 59% mixed-signal articles) is unlearnable for a 1B-param student; ~€41–46 oracle spend before PARKED indefinitely. See `memory/thriving-v1-scoring.md` and ADR-015. **Don't retry** "this is NOT [other lens], score 0–2" exclusion clauses in oracle prompts, and don't strip glue dimensions (e.g. `social_cohesion_impact`) trying to enforce orthogonality — lenses are overlapping perspectives, and ADR-014 percentile normalization handles cross-tab ranking already. **Cross-ref:** structurally the same lesson as [ovr.news hypothesis-log](https://github.com/ducroq/ovr.news/blob/master/docs/hypothesis-log.md) Dead Ends entry "Stack rules in the brand-voice prompt" (#229, 2026-06-01/02) — adding rules surfaces new failure modes, not fewer.

- **`score_scale_factor` linear stretch as cross-filter normalization** (Mar 2026, superseded by ADR-014). Filters' production distributions differ structurally (uplifting passes 62.8% as MEDIUM+; nature_recovery 0.3%); linear stretching can't fix a non-linear distribution mismatch. HOME tab `max(weighted_average)` made uplifting dominate, articles opened in wrong tabs. Rejected alternatives tested: z-score normalization (assumes normal — NR p95 stuck at 6.84), P99 max-scaling (NR p90 normalized to 1.94), val-set CDF (54% of NR articles tied at one value because val set has 70% at score 1.0). See `memory/gotcha-log.md` "score_scale_factor Is Linear" and ADR-014. **Don't retry** any global linear or moment-based normalization (`score_scale_factor`, z-score, P99 max-scaling, val-set CDF) as cross-filter harmonization. `score_scale_factor` remains only as the fallback path for filters that don't yet have `normalization.json`.

- **Universal noise prefilter beyond commerce** (sustainability_technology active learning, 2026-01-31). Initial plan: a universal noise filter for software tutorials, farming, policy, etc. — sustainability_tech showed 40% oracle waste on out-of-scope articles. Analysis showed each category is *signal* for another filter: farming → nature_recovery, software tutorials → augmented-engineering, policy → policy_analysis. Source-exclusion experiments tested at 33–56% precision (would block legitimate content like "heat pump retrofit testing" scoring 4.8). Only commerce is universal noise, already covered by `commerce_prefilter` v2 at 97.8% F1. See `docs/adr/004-universal-noise-prefilter.md` (Proposed → de-facto closed) and the repurposed `datasets/training/universal_noise_prefilter/`. **Don't retry** building a second "universal noise filter" for software / farming / policy. Accept ~30–40% oracle waste during training — the "wasted" zeros are valuable negative training examples for the student. Use filter-specific keyword prefilters + per-filter student scope.

- **`% normalized < 0.5` as a filter-health metric** (LD#76 audit, 2026-07-31). The metric drove LD#76's "filters crush good content" framing, but for any anchored-CDF filter it is definitionally ≈ `1 − MEDIUM+ base rate` — everything below the op-point clips to ~0 *by construction*. The healthy reference investment_risk is itself 75.1% "invisible" by it; cultural_discovery's 99% and belonging's 98% were mostly honest needle base rates over an unscreened firehose. The 11-agent audit (LD#76 issuecomment-5140079896) found the real defects elsewhere (two stale fits, a NexusMind tier double-cut, a dead prefilter). **Don't retry** `% norm < 0.5` (or any below-op-point share) as a filter-health headline — it conflates base rate with pathology. Use the ir-derived criteria instead: raw p90 vs op-point, populated spread-out MEDIUM+ band, intact good-vs-chaff separation, anchored fresh fit.

- **Diagnosing raw-score health from production files without checking score provenance** (#75, falsified by LD#76 audit 2026-07-31). #75 declared nature_recovery v4 "scale-collapse" (raw p90 0.72, fires near-zero for everything) from Jul-21 production files. Two artifacts stacked: 94% of nr production rows are **stage-1 e5-probe estimates capped at 0.75** (hybrid inference short-circuit — the low end of the raw distribution is probe output, not model output; density cliff at 0.75 reproduces at 4.1×), and the Jul-21 files **predate normalization entirely** (`normalization_method='none'` on 1891/1891 rows). The model, op-point, and fit are all verified sound. **Don't retry** reading a hybrid filter's raw production distribution as a model signal without first splitting rows by inference stage (until `stage_used` is emitted: probe-capped values cluster at the stage-1 threshold) and checking `normalization_method` on the rows you're aggregating.

- **`.nexusmind-owns` manifest as cross-repo divergence-management strategy** (#50, 2026-04-28 → retired 2026-05-04). The manifest declared `filter_base_scorer.py` and `hybrid_scorer.py` as "NexusMind-owned, won't be overwritten." On 2026-04-16 NexusMind's normalization application code was silently deleted; both copies became byte-identical (399 lines, no normalization). The manifest *claimed* divergence; nothing checked. All 7 filters silently de-normalized for **18 days** — acute on nature_recovery v2 (median 0.0, p90 0.3, 0.06% ≥4.0). Fixed by extracting to a wrapper class (`NexusMind/src/scoring/production_scorer.py`); manifest is now empty-by-default and any entry requires a tracked issue + deadline. See `memory/gotcha-log.md` "Manifest as Anti-Pattern" and ADR-014 implementation amendment. **Don't retry** an "X is owned by the other repo" manifest as the *primary* divergence-management mechanism — default to extraction (composition over inheritance, wrapper classes). "By design" is a claim about the implementation; verify by reading the runtime, not the design doc. **Cross-ref:** same family as ovr.news hypothesis-log Dead Ends entry "NexusMind embedding-dedup as sole source of truth" (corroboration cluster, seeded 2026-06-05) — both are cases where a shared assumption between repos was load-bearing but never verified at runtime.

- **Treating a filter's `config.yaml` as evidence that the thing it configures is running** (NM#284, 2026-08-01). Every filter declared `prefilter: enabled: true` with an `expected_pass_rate`; the GPU scorer built each one with `use_prefilter=False` and called `score_batch(skip_prefilter=True)`. Per-filter prefilters therefore **never ran in production from 2026-02-10 to 2026-08-01** (~6 months) while stamping `passed_prefilter: true` on 100% of articles. The layer looked alive because it *is* alive in the llm-distillery oracle/training path (where it saves measured spend) and because the separate commerce prefilter visibly drops articles in production — so "prefiltering works" was true at system level and false at filter level. Scope precisely — the dead layer is the **per-lens rule prefilter** only; the e5 probe, commerce/obituary/violence gates, and the NM#189 source-type allowlist all run (each verified). **Don't retry** inferring runtime behavior from config keys, and don't accept "the config says enabled" as verification. **The diagnostic that settles it:** measure the component *in-path on the pre-drop stream* — the shadow log reports cd `observed_pass` 0.255 pooled at the scorer, which would read ≈1.000 if the gate were enforcing upstream. **Don't retry** the more tempting version of this: replaying the component over rows from `data/filtered/*/filtered_*.jsonl` and diffing against the stamped rate. That file only receives rows where `passed_prefilter` is true NexusMind `scripts/main.py`’s `if result["passed_prefilter"]:` write guard, so its "100% passed" is an artifact of the file's own write condition — the first version of this entry cited exactly that and had to be retracted. **A reproduction is only as good as the population you reproduce it on; before using a data source as a denominator, establish what it is filtered on.** Generalizes to any declared-rate component: assert observed against declared in production, or the declaration is decoration. Same family as the `.nexusmind-owns` entry above and `memory/gotcha-log.md` "LD#80 rollback was a production no-op" — verify the call path, not the diff.

- **Reading a lens-specific block rate off a prefilter without splitting out the shared base rules** (NM#284 sizing, 2026-08-01). First pass reported "prefilters would block 38.8% of inferences" and that nature_recovery v4 / solutions v6 "block identically, so the template was copied and never specialized." Splitting blocks by rule: **24.8 of the 38.8 points is `content_too_short`**, a `BasePreFilter` rule blocking *the identical 853 articles* for every filter — which is why the two block sets were byte-identical. Lens-specific blocking is 14.0%, and **88% of that is cultural_discovery alone**. The architectural consequence is the opposite of the first read: the win is one **global** short-content gate before fan-out, not six per-filter gates. **Don't retry** quoting a prefilter's total block rate as lens signal — always split base-class rules (length, missing content) from lens rules first. Corollary correction: nature_recovery v4's zero lens blocks are *deliberate and documented* (v4 removed topic/decline gates — English-only, cost 21.6% recall — delegating screening to the multilingual e5 probe), so "lens block rate must be non-zero" is the wrong harmonization criterion. The right one is **observed pass rate matches declared, and `description` matches actual behavior** (LD#90).

- **A global pre-fan-out `content_too_short` gate** (NM#284 stage 2 proposal, 2026-08-01 → REFUTED 2026-08-02). The length floor blocks ~33% of the corpus identically for every filter, so promoting it before fan-out looked like a free ~33% scoring saving. Two oracle tests killed it. At n=60/group, short content that clears an op-point is **as likely to be genuine as long content** (uplifting: 67% vs 65% oracle-validated), so the gate would discard ~78 genuine surfacing uplifting articles per 8 cycles to remove ~39 bad ones — and the loss skews to `spanish_*` / `gn_africa_*` / `gn_central_america` / `french_*`, i.e. NM#231's under-served population. **Don't retry** promoting `MIN_CONTENT_LENGTH` to a gate at any level. The one filter with a genuine short-content defect (`solutions v6`, DiD −1.13) wants a **cap/penalty** sized to its own ~49 FPs per 8 cycles — see #93 and `memory/prefilter-length-floor-hypotheses.md`. **#93 shipped 2026-08-03 (LD side):** the floor is now labelling-time only, length is stamped on every scoring result, and a per-filter `short_content.cap` exists — **set on nothing**, because solutions' DiD is still confounded with a selection artifact. Fitting that cap without the second-op-point re-run would be the same mistake one level down.

- **Explaining the six-filter prefilter pass-rate cluster as a truncation artifact** (NM#285, 2026-08-01 → REFUTED 2026-08-02). Four filters clustered at 0.638–0.649 and the scorer's `Article` contract carries only `{title, content}`, so "url/source rules are inert, therefore every filter collapses toward the shared base rule" was the obvious reading. A same-row full-vs-truncated replay (n=8,283) put the effect at **+0.0000** for the two filters at the centre of the cluster and **+0.0097** at worst. The mechanism was real; the magnitude was off by an order of magnitude, and the actual cause was that `nature_recovery v4` and `solutions v6` have no lens rules at all. **Don't retry** widening the GPU `Article` contract (Option A) or moving prefilters pipeline-side (Option C) *on truncation grounds* — both were declined on this measurement. A separate, larger bias does exist in the same log: the denominator counts articles `source_filter` discards after scoring (−0.129 on investment_risk), now stated on every shadow line.

- **MAE as a cross-filter quality metric — and as grounds for any calibration change** (2026-08-09, killed by the owner within an hour of being published). An agent measured `uplifting v7` at MAE 0.84 against solutions 0.48 / nature_recovery 0.50 / belonging 0.49 / investment_risk 0.47, called it "the weakest of the six", and recommended refitting or dropping its calibration because calibrated MAE (0.8398) was *worse* than uncalibrated (0.8110). **Both claims were artifacts of the metric.** MAE weights every article equally while the product only cares about the thin band at the op-point; and each filter's test split has its own positive rate — `uplifting v7` **32.7%**, `solutions v6` **16.2%**, `nature_recovery v4` **15.3%** — so a more enriched split carries larger per-article error *for identical model quality*. Measured on uplifting's 660 held-out rows: per-article MAE is **1.1954 on oracle-positives vs 0.6668 on negatives (1.79×)**, and holding those fixed, composition alone explains **+0.0919 of the 0.3435** gap to nature_recovery. (Note the second retraction, against itself: that is ~27%, **not all of it** — the residual may be real, it is simply not the objective.) On the *decision*, calibration is indistinguishable: uncalibrated recall 0.7593 / spec 0.9122 / f1 0.7828 vs calibrated 0.7361 / 0.9189 / 0.7737 — 5 articles of 660 change side, inside the 37-row indeterminate band. **Don't retry** ranking filters on MAE, or changing a calibration on an MAE reading. **The same trap one level down: precision is base-rate dependent too.** Only **recall** and **specificity** are conditional on the true class and comparable across splits — report both, always with the split's positive rate. Now **ADR-023** and a CLAUDE.md Hard Constraint.

- **"The isotonic calibrator crushes the scale" as the explanation for the 173× cross-lens surfacing spread** (2026-08-09, proposed and refuted the same day by the agent that proposed it). The mechanism is real and measured: `nature_recovery v4`'s `recovery_evidence` map jumps **+2.47 over a 0.06 step in student output** (2.8125 → 1.333, 2.875 → 3.80), and **>52% of the student's output range maps to calibrated ≤1.33** while the gate is 3.75. Isotonic is monotone, so ordering survives and the metric scale does not; the crush tracks calibration-set size and label bimodality (nr's val n=389 vs investment_risk's 1,045). It looked like the whole answer. **It is worth ~3 articles per cycle.** 160 production articles stratified by student band and graded by DeepSeek (nr's own oracle): band A (surfacing) **26/30 oracle-positive = 0.87 precision**, matching the recorded 0.848; bands D+E (student <1.0, **96.7% of the corpus**) returned **0 of 50** with an oracle *maximum* of 1.05. Implied ~8 oracle-positives/cycle against ~5 surfaced → recall ~0.6, matching the gate's recorded 0.65. **`nature_recovery` is behaving as specified; the corpus genuinely holds ~0.36% of that content.** **Don't retry** explaining a low surfacing rate by a calibration pathology before oracle-grading a *stratified sample of the actual production distribution* — a mechanism can be real, measured, and still not be the lever. And **don't read a needle filter's low surfacing count as a defect at all** until the base rate is established: the outlier in that table was `investment_risk` at 24.2%, not `nature_recovery` at 0.14%.

## Maintenance

- Add an entry when an experiment is concluded as "don't retry" (not "paused — may revisit"). Paused experiments belong in `memory/thriving-v1-scoring.md` (and similar) or in an ADR; they should only land here once the door is closed.
- Keep entries to one paragraph (3–5 sentences). If the entry grows a multi-step rationale, link out to an ADR or gotcha-log entry instead of inlining it.
- The `**Don't retry** <scope> — <reason>` closing is mandatory; that's the line a future agent reads at session start to avoid the re-experiment.
- Reviewed as part of end-of-session `/curate` flow: "did any approach fail today that future-you should not retry?"
